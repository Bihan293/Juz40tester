# Админ-панель

Админ-панель — раздел бота только для администраторов: статистика, поиск пользователей и смена их подписки, рассылки. Кроме того, у администратора в тестах виден правильный ответ, а покупки за Telegram Stars проходят без оплаты (тестовый режим).

## Кто администратор

Администраторы задаются переменной окружения `ADMIN_IDS` — Telegram id через запятую (пробел и `;` тоже подходят):

```
ADMIN_IDS=123456789,987654321
```

На Render: Environment → `ADMIN_IDS` → свой Telegram id → перезапуск сервиса. Правок кода и базы не нужно. Узнать свой id можно у любого бота вида `@userinfobot`.

Это та же переменная, что у команд `/grant`, `/revoke`, `/subinfo`, `/refund` (docs/SUBSCRIPTIONS.md). Неверное значение (не число) не даёт боту стартовать — ошибка будет в логе.

### Защита

- Проверка делается **на сервере** при каждом действии, а не только скрытием кнопок:
  - роутер проверяет `ADMIN_IDS` для каждого callback `adm:…` и каждого сообщения админ-диалога;
  - сервисы (`AdminService.SetPlan`, `CreateBroadcastDraft`, `ConfirmBroadcast`, `CancelBroadcast`, `BillingService.AdminBypassPurchase`) проверяют администратора ещё раз и возвращают `ErrNotAdmin`.
- Для обычного пользователя панели «не существует»:
  - кнопки «🛠 Админка» в меню нет;
  - `/admin` и текст «🛠 Админка» обрабатываются как неизвестная команда (главное меню);
  - поддельная кнопка `adm:…` только гасит «часики» — без текста и без действий.
- Все изменения пишутся в журнал `admin_actions` (кто, что, над кем, детали «было/стало») и в лог (`admin: tg … set_plan …`). Метрика — `admin_actions_total{action}`.

## Вход

- Кнопка «🛠 Админка» в нижнем меню (только у админов).
- Команда `/admin`.

Меню: 📊 Статистика · 👥 Пользователи · 📣 Рассылка.

## 📊 Статистика

Все цифры считаются на момент открытия (кнопка «🔄 Обновить»). «Сегодня» — календарный день по `QUOTA_TZ` (Asia/Almaty), «активность» — по календарю серий (UTC+5).

- **Пользователи:**
  - всего;
  - новые за сегодня / 7 / 30 дней;
  - активные за сегодня / 7 / 30 дней (`users.last_active_date`);
  - сколько заблокировали бота (`users.blocked_at`, отмечается рассылкой).
- **Тесты:**
  - начато сегодня;
  - пройдено сегодня / за 7 дней / всего;
  - в процессе сейчас.
- **Подписки:** число активных Plus / Pro / Premium (с учётом `SUB_GRACE_MIN`). Free = все остальные.
- **Платежи (только реальные Stars):**
  - число и сумма — всего / за 30 дней / сегодня;
  - возвращённые и ждущие возврата;
  - отдельно — число тестовых покупок админов (они в выручку не входят).
- **Очереди:**
  - генерация `generation_jobs` (pending / running по видам) и ошибки за сутки;
  - переводы;
  - очередь апдейтов кластера (`tg_update_queue`: в работе / dead);
  - активные рассылки.

Запросы — несколько агрегатов по индексам (`users(created_at)`, `users(last_active_date)`, `test_attempts(started_at)`, `test_attempts(completed_at) WHERE completed`). Кэша нет: экран открывают руками и редко.

## 👥 Пользователи

«👥 Пользователи» → бот ждёт запрос. Варианты:

| Запрос | Как ищется |
|---|---|
| `@username`, `t.me/username` | точное совпадение без учёта регистра (индекс `lower(username)`), если нет — по началу ника |
| число | Telegram id **или** внутренний id |
| любой другой текст | часть имени/фамилии или ника (`ILIKE`, спецсимволы `%` и `_` экранируются) |

Нашёлся один — сразу открывается карточка. Нашлось несколько (до 10, свежие по активности первыми) — список кнопок. Запрос можно уточнять, пока режим поиска не закрыт (любая команда или кнопка меню выходит из него; через 30 минут он забывается сам).

### Карточка

- Telegram id и внутренний id, ник, имя, дата регистрации.
- Последняя активность и серия 🔥, язык тестов. Если пользователь заблокировал бота — с какого момента.
- Прохождения:
  - сегодня;
  - всего;
  - сколько попыток всего;
  - сколько в процессе;
  - когда был последний старт теста;
  - сколько списано сегодня по дневному лимиту.
- Платежи: число и сумма реальных Stars, плюс тестовые покупки админа.
- Подписка: план, срок действия (и сколько дней осталось), источник — «оплата Stars» или «выдана админом», дневной лимит.
- Слабые темы — по 3 худших на предмет, те же правила, что в «🎯 Слабые темы».
- Последние 3 действия админов над этим пользователем.

### Изменить подписку

«⭐ Изменить подписку» показывает Бесплатный / Plus / Pro / Premium. Текущий план отмечен «✅ … — текущий».

- **Платный план:** выбор срока 7 / 30 / 90 / 365 дней (от текущего момента) → экран подтверждения «выдать Pro на 30 дн. (до …) пользователю …?» → «✅ Подтвердить». План применяется сразу.
- **Free:** подтверждение «снять платную подписку» → текущий план отзывается.

Используется тот же слой, что у `/grant` и `/revoke` (`BillingService.GrantDetailed` → `user_subscriptions`, `source='admin'`). Поэтому:
- дневной лимит меняется мгновенно;
- выданный админом план не продлевается сам и заканчивается в срок.

Что происходит со Stars-подпиской пользователя (решение владельца: уже оплаченное не возвращается и не компенсируется, остальное админ разруливает сам):
- **Free:** автопродление подписки в Telegram отменяется — в следующем месяце звёзды списаны не будут.
- **Платный план:** со следующего периода пользователь платит цену выбранного плана (Plus 10⭐, Pro 40⭐, Premium 50⭐ — по каталогу). Подписка того же плана по той же цене остаётся и продлевается. Любая другая подписка отменяется (её цену поменять нельзя), а по окончании выданного срока бот один раз присылает пользователю ссылку на подписку выбранного плана.
- Если продление старой подписки всё-таки пришло (гонка или отмена не удалась), платёж принимается без возврата, выданный админом план не меняется, автопродление отменяется ещё раз.
- После подтверждения бот пишет админу, что сделано с подпиской: отменена, оставлена или отменить не удалось.

Каждая смена пишется в `admin_actions` (`set_plan`, детали `plan=pro days=30 until=… (было: free)`). Команды `/grant`, `/revoke`, `/refund` теперь тоже пишутся в журнал (`cmd_grant`, `cmd_revoke`, `cmd_refund`).

Если подписки выключены (`SUBSCRIPTIONS_ENABLED=0`), кнопки смены подписки нет, остальная панель работает.

## Правильные ответы в тестах у админа

У администратора в каждом вопросе правильный вариант отмечен «✅» — и в тексте, и на кнопке. Под вариантами есть строка «🛠 Админ: правильный ответ — B».

- Меняется **только отображение**. Кнопки отправляют те же данные, ответ проверяется и засчитывается тем же кодом.
- У обычных пользователей ничего не меняется (покрыто тестами).
- **Решение по лимиту:** прохождения админа считаются и списываются **как у всех** — `test_completions`, `daily_usage`, статистика, прогресс 🟢/🟡, слабые темы.
  - Почему так: админ видит поведение бота «как пользователь», а подсчёт и дневной лимит не получают особого случая, который мог бы их сломать.
  - Если лимита не хватает, админ выдаёт себе Premium через панель или покупает план в тестовом режиме (ниже).
  - Плата за это: прохождения админа попадают в общую статистику. Для одного-двух админов это незаметно.

## Покупки админа без оплаты (тестовый режим)

Для id из `ADMIN_IDS` любая покупка за Stars проходит сразу, без счёта и окна оплаты:
- «⭐ Купить …» / «⬆️ Перейти на …» в «⭐ Подписка»;
- новый тест по слабым темам.

### Как это устроено (`BillingService.AdminBypassPurchase`)

1. Сервис заново проверяет администратора (`ErrNotAdmin`).
2. Применяются **те же правила**, что в `pre_checkout_query`: уже активный план купить нельзя, на более дешёвый перейти нельзя, тест по слабым темам — только при наличии слабых тем. Отказ показывается текстом «🛠 Тестовая покупка отклонена: …».
3. Создаётся «платёж» с `telegram_payment_charge_id = admin-bypass:<случайный id>`, `amount` = цена, `payments.admin_bypass = TRUE`.
4. Он проходит через тот же конвейер, что и настоящий `successful_payment`:
   - подписка: новая / апгрейд / продление, на 30 дней;
   - тест по слабым темам: оплаченный заказ, сборка теста, выдача.
   
   Пользователь видит те же сообщения, что при настоящей оплате, плюс строку «🛠 Режим администратора: покупка проведена без оплаты».

### Отличия от настоящей оплаты

- Подписка сохраняется с `source='admin'` и без `sub_charge_id`: в Telegram нет подписки, нечего продлевать или отменять. `editUserStarSubscription` для таких id никогда не вызывается.
- **Возвратов нет.** Если такой платёж нужно «вернуть» (заказ не собрался, `/refund`, отказ по правилам), он сразу помечается `refunded`. В очередь возвратов не попадает (`ClaimDueRefunds` исключает `admin_bypass`), `refundStarPayment` не вызывается.
- В выручку статистики не входит, считается отдельно.
- Журнал: `admin_actions.action = bypass_purchase`. Метрика: `billing_payments_total{decision="…_admin_bypass"}`. Лог: `billing: ADMIN BYPASS purchase …`.

## 📣 Рассылка

### Создание

Пошагово:
1. **Текст.** Форматирование (жирный, ссылки и т. п.) сохраняется — бот хранит `entities` исходного сообщения. Можно сразу прислать фото или видео с подписью, тогда шаг 2 пропускается.
2. **Фото или видео** — необязательно, кнопка «Без медиа». Текст становится подписью, лимит Telegram — 1024 символа; текст без медиа — до 4096.
3. **Кнопки-ссылки** — необязательно, кнопка «Без кнопок». Одна кнопка на строку:
   ```
   Наш канал | https://t.me/juz40
   Сайт | https://example.com ;; Чат | https://t.me/juz40chat
   ```
   `;;` ставит несколько кнопок в один ряд. Допустимы ссылки `https://`, `http://`, `tg://`. Ограничения: до 8 рядов, до 3 кнопок в ряду, текст кнопки — до 64 символов.
4. **Предпросмотр.** Бот присылает админу ровно то сообщение, которое получат пользователи (тем же методом отправки). Если Telegram его не принял (битая ссылка, неверный файл), об этом видно сразу, и рассылка не запускается.
5. **Подтверждение** «✅ Отправить (N)». N — все пользователи, кроме заблокировавших бота. Повторное нажатие ничего не дублирует. Есть «✏️ Начать заново» и «❌ Отмена».

Состояние диалога хранится в `admin_sessions`, не в памяти процесса: при `web` + N `worker` следующее сообщение админа может обработать другой воркер.

### Отправка

- Отправляет фоновый `BroadcastService`. Он работает в каждом процессе, который обрабатывает апдейты (`ROLE=all` или `ROLE=worker`). Инстанс `ROLE=web` только принимает вебхук.
- **Одна рассылка — один отправитель.**
  - Рассылку забирает один воркер по аренде (`broadcasts.locked_by/locked_until`, продлевается во время отправки).
  - Одновременно во всём кластере отправляется только одна рассылка, поэтому лимит не умножается на число воркеров.
  - Если воркер умер, аренда истекает, и рассылку подхватывает другой.
- **Скорость.**
  - `BROADCAST_RPS` сообщений в секунду; по умолчанию 2/3 от `TG_MAX_RPS`, то есть 16 при 25.
  - Поверх действует общий ограничитель клиента `TG_MAX_RPS` (в кластере общий через Redis/Postgres), так что обычным пользователям всегда остаётся запас.
- **429 Too Many Requests.**
  - Telegram сообщение не принял, поэтому повтор безопасен.
  - Получатель возвращается в очередь на `retry_after` секунд, а отправитель ждёт столько же (до 30 с): лимит общий на весь бот.
- **403 / «user is deactivated».** Получатель — «заблокировал бота», у пользователя ставится `users.blocked_at`.
  - Следующие рассылки его пропускают.
  - Как только он снова напишет боту или нажмёт кнопку, отметка снимается.
- **5xx и сетевые ошибки** — до 3 попыток с паузой 30 / 60 с, затем «ошибка». Прочие ответы 400 (например, «chat not found») — сразу «ошибка».

### Устойчивость к перезапуску и защита от повторов

Прогресс хранится по каждому получателю (`broadcast_recipients`):
- `pending` → `sending` (HTTP-запрос в пути) → `sent` / `failed` / `blocked` / `canceled`;
- отметка `sending` пишется **до** запроса, результат — сразу **после**.

Перезапуск:
- **Плавная остановка (SIGTERM).** Текущее сообщение досылается и записывается, аренда освобождается, после старта отправка продолжается с первого `pending`.
- **Падение.** Строка, оставшаяся в `sending`, не отправляется повторно: возможно, Telegram её уже доставил. Она закрывается как `failed` с текстом «прервано перезапуском (доставка неизвестна)». Поэтому при падении в самый момент отправки одно сообщение в худшем случае не дойдёт, но двух сообщений не будет никогда.
- **Сетевой сбой без ответа Telegram** (соединение не установлено) повторяется. При таймауте уже отправленного запроса повтора нет: он считается «доставка неизвестна».

### Итог, отмена, история

- Когда получателей не осталось, рассылка закрывается (`done`) ровно один раз, и создатель получает итог:
  - всего получателей;
  - отправлено;
  - заблокировали бота;
  - ошибки;
  - время.
- «📈 Прогресс» / «🔄 Обновить» показывают живые цифры и оценку оставшегося времени.
- «⛔ Остановить» (с подтверждением): неотправленные получатели получают статус `canceled`, отправитель останавливается на следующем сообщении. Уже отправленное отозвать нельзя.
- «📜 Прошлые рассылки» — последние 10 с номерами, статусом и счётчиками.
- Черновики, не подтверждённые за 7 дней, удаляются.

### Метрики и лог

- Метрика `admin_broadcast_messages_total{result=sent|blocked|failed|retry|rate_limited}`.
- Строки лога `broadcast N: sending … / done in … — total, sent, blocked, failed`.

| Переменная | По умолчанию | Что делает |

## Что проверить руками после деплоя

1. Добавить свой id в `ADMIN_IDS`, перезапустить. Отправить `/start`: должна появиться «🛠 Админка». С другого аккаунта кнопки нет, `/admin` открывает обычное меню.
2. Открыть «📊 Статистика».
3. Найти себя по `@нику`. Выдать второму аккаунту Pro на 7 дней: на его «⭐ Подписка» должен быть Pro. Вернуть Free.
4. Открыть тест: у админа ✅ на правильном варианте, у второго аккаунта нет.
5. Нажать «Купить Plus» у админа: план включается сразу, окна оплаты нет. В статистике растут «тестовые покупки», выручка не меняется.
6. Сделать рассылку с фото и кнопкой. Получить предпросмотр, отправить, дождаться итога. Со второго аккаунта заранее заблокировать бота: в итоге он попадёт в «Заблокировали бота».
