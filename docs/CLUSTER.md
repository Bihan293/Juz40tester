# Кластерный режим: web + N worker

По умолчанию (`ROLE=all`) бот работает как раньше: один процесс принимает вебхук, обрабатывает апдейты в памяти (пул воркеров + ограниченная очередь), генерирует и переводит тесты. Ничего настраивать не нужно, Redis не нужен.

Когда одного процесса мало, бот делится на роли:

| Роль | Что делает | Что НЕ делает |
|---|---|---|
| `ROLE=web` | принимает `POST /telegram/webhook`, проверяет секрет, кладёт апдейт в общую очередь и сразу отвечает 200; ставит webhook; отдаёт `/health`, `/ping`, `/metrics` | не обрабатывает апдейты, не генерирует, не переводит, не чистит |
| `ROLE=worker` | забирает апдейты из очереди и обрабатывает их; воркеры генерации и перевода, LISTEN, reaper'ы, quality sweep, ежесуточная очистка, bootstrap цепочки, бэкфиллы; отдаёт `/health`, `/ping`, `/metrics` (для health check платформы) | не принимает вебхук (`/telegram/webhook` → 404), не вызывает `setWebhook`, не нужны `WEBHOOK_URL`/`WEBHOOK_SECRET` |
| `ROLE=all` | всё в одном процессе (как раньше) | — |

Миграции применяет каждый процесс при старте (они сериализованы advisory-локом, одновременный старт безопасен).

## Очередь апдейтов

`QUEUE_BACKEND=postgres` (по умолчанию для `web`/`worker`) — таблица `tg_update_queue` (миграция `000025`, только добавляет объекты):

- **Идемпотентность в БД.** `update_id` — первичный ключ; повторная доставка Telegram (потерянный 200, деплой, второй web-инстанс) — `INSERT … ON CONFLICT DO NOTHING`, ответ 200 без повторной обработки. Обработанные строки хранятся `UPDATE_DONE_TTL_HOURS` (48 ч > 24 ч окна повторной доставки Telegram), потом удаляются батчами.
- **Порядок одного пользователя.** Строка забирается (`FOR UPDATE SKIP LOCKED`) только если у этого же `user_key` (id отправителя) нет более ранней строки в `pending`/`processing`. Значит, два апдейта одного пользователя никогда не обрабатываются параллельно и всегда идут по возрастанию `update_id` — на любом числе воркеров и инстансов. Разные пользователи обрабатываются параллельно.
- **Пробуждение.** Вставка и `pg_notify('tg_updates')` — один запрос; воркеры слушают канал на прямом соединении (то же, что `gen_jobs`/`tr_jobs`), запасной опрос раз в 3 с. Воркер, получивший апдейт, будит следующего — всплеск расходится по всему пулу.
- **Lease + heartbeat + reaper.** Взятый апдейт продлевается heartbeat'ом каждые `UPDATE_LEASE_SEC/3`; если воркер умер (kill -9, OOM, падение машины), reaper любого воркера через `UPDATE_LEASE_SEC` (45 с) возвращает апдейт в очередь. Все операции завершения «огорожены» (`locked_by` + номер попытки), поэтому запоздавший воркер не может закрыть чужую попытку.
- **Ретраи и dead-letter.** Падение обработчика (panic) → повтор с backoff 2 с, 4 с, 8 с … ≤ 1 мин; после `UPDATE_MAX_ATTEMPTS` (3) апдейт получает статус `dead` (хранится `UPDATE_DEAD_TTL_DAYS`, 14 дн.), следующие апдейты пользователя идут дальше. Просмотр и повтор:
  ```sql
  SELECT update_id, user_key, attempts, last_error, payload FROM tg_update_queue WHERE status = 'dead' ORDER BY finished_at DESC LIMIT 20;
  UPDATE tg_update_queue SET status = 'pending', attempts = 0, available_at = now(), finished_at = NULL WHERE update_id = <id> AND status = 'dead';
  ```
- **Backpressure.** Когда в очереди `UPDATE_QUEUE_MAX` (20 000) необработанных апдейтов, web отвечает 503 + `Retry-After` — Telegram доставит позже. Счётчик кэшируется на 1 с (один `count(*)` в секунду на web-инстанс, а не на каждый апдейт). Недоступная БД → тоже 503 (ничего не теряется).
- **Graceful shutdown.** Web сразу отвечает 503; worker перестаёт брать новые апдейты, дожидается текущих (до 20 с), а не успевшие — возвращает в очередь без списания попытки.

`QUEUE_BACKEND=redis` — та же семантика на Redis (Lua-скрипты, ключи под hash-tag `{REDIS_PREFIX}`, работает и в Redis Cluster): список апдейтов на пользователя, `ready`/`busy` ZSET, owner-токены для fencing, маркер идемпотентности `seen:<update_id>` с TTL, dead-letter список (последние 10 000), пробуждение через pub/sub.

`QUEUE_BACKEND=memory` — прежний in-process диспетчер; возможен только с `ROLE=all`.

## Лимиты Telegram между инстансами

| `RATELIMIT_BACKEND` | `TG_MAX_RPS` | Тап-троттлинг `USER_ACTION_INTERVAL_MS` |
|---|---|---|
| `memory` (по умолчанию для `all`) | на процесс | на процесс |
| `postgres` (по умолчанию для `web`/`worker`) | делится поровну между живыми отправляющими инстансами (`cluster_instances`, heartbeat 15 с, живой = heartbeat < 45 с; web не считается): 2 воркера при 28 rps → по 14 rps | на процесс (порядок апдейтов одного пользователя и так сериализован очередью) |
| `redis` | ОДИН общий token bucket (GCRA в Lua) на весь кластер; 429 ставит на паузу все инстансы | общий (`SET NX PX`) |

Ограничение `postgres`: деление статическое — простаивающий воркер не отдаёт свою долю другим, а при падении инстанса его доля перераспределяется через ≤ 45 с. Для точного общего лимита — `redis`. Если Redis недоступен, клиент Telegram автоматически переходит на локальный лимитер (сообщения не зависают), тап-троттлинг пропускает (fail-open).

## Redis (опционально, «на будущее»)

`REDIS_URL` пуст → Redis не используется вовсе. Даже с `REDIS_URL` Redis включается ТОЛЬКО для бэкендов, явно переключённых в `redis`:

```
REDIS_URL=redis://:password@host:6379/0
QUEUE_BACKEND=redis       # очередь апдейтов + шина событий
RATELIMIT_BACKEND=redis   # общий TG_MAX_RPS + общий тап-троттлинг
CACHE_BACKEND=redis       # общий кэш лидербордов (второй уровень)
REDIS_PREFIX=juz40
```

## События между инстансами

Пользователь ждёт генерацию/перевод в процессе, который обработал его тап, а задача может выполниться на другом воркере. В кластерном режиме по завершении задачи публикуется событие (PostgreSQL `NOTIFY juz_events` или Redis pub/sub при `QUEUE_BACKEND=redis`), и все инстансы сразу будят своих ожидающих — без него они узнали бы о готовности только по запасному опросу (10–30 с).

## Деплой на Render: web + N worker

1. **Web Service** (Docker): `ROLE=web`, `BOT_TOKEN`, `DATABASE_URL`, `WEBHOOK_URL`, `WEBHOOK_SECRET`. Можно 1–2 инстанса; маленький пул: `DB_MAX_CONNS=5`, `DB_MIN_CONNS=1`.
2. **Background Worker** (тот же Docker-образ): `ROLE=worker`, `BOT_TOKEN`, `DATABASE_URL`, ключи ИИ (`GROQ_API_KEY`, `DEEPSEEK_API_KEY`), лимиты генерации. Масштабировать числом инстансов (N). `INSTANCE_ID` можно не задавать (по умолчанию `hostname-pid`, уникален).
3. Бюджет соединений Neon: `web × DB_MAX_CONNS + N × (DB_MAX_CONNS + 3)` ≤ лимита. Обработчиков апдейтов на воркер — `UPDATE_WORKERS` (по умолчанию `DB_MAX_CONNS − резерв фоновых задач`, ≤ 32).
4. Генерация/перевод/очистка безопасны на N воркерах: задачи берутся `FOR UPDATE SKIP LOCKED`, quality sweep — под advisory-локом, дневной cap DeepSeek и лимиты генераций — в БД.
5. Переход с `ROLE=all`: можно без простоя — поднять воркеры (`ROLE=worker`), затем переключить существующий сервис на `ROLE=web`. Обратно — `ROLE=all` (очередь в БД дочищают оставшиеся воркеры; `all` + `QUEUE_BACKEND=postgres` тоже допустимо — тогда один процесс и принимает в очередь, и обрабатывает её).

Мониторинг (`/metrics`): `tg_updates_enqueued_total{result=new|duplicate|full|error|ignored}`, `tg_updates_processed_total{result=ok|retry|dead|dropped|released}`, `tg_updates_reaped_total`, гейджи `tg_update_queue_pending|processing|dead`, `cluster_live_senders`.
