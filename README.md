# JUZ40 Tester

Telegram-бот для подготовки к ЕНТ/УБТ для школьников 9–11 классов (JUZ40). Стек: Go, Telegram Bot API (webhook), PostgreSQL (Neon) + pgx/v5, **Groq API (бесплатно: GPT-OSS 120B + Qwen 3.8 27B)** + DeepSeek API (платный резерв), Docker, Render.

## 💸 Groq: бесплатные модели вместо DeepSeek

С `GROQ_API_KEY` почти вся ИИ-работа уходит на бесплатный тариф Groq, DeepSeek вызывается только как резерв:

| Задача | Модель | Резерв |
|---|---|---|
| Перевод теста на казахский | `qwen/qwen3.8-27b` (instruct, без рассуждений — быстро) | `openai/gpt-oss-120b` → DeepSeek |
| Генерация chain-тестов | `openai/gpt-oss-120b` (reasoning medium; low на повторе) | Qwen → DeepSeek (не более 2 попыток Groq) |
| Тест по слабым темам | `openai/gpt-oss-120b` (reasoning low) | Qwen → DeepSeek |

Лимиты Free-плана (на каждую модель): **30 RPM · 1 000 RPD · 8 000 TPM · 200 000 TPD**, причём 8 000 TPM — это ещё и максимальный размер одного запроса (prompt + max_tokens). Бот соблюдает их локально (скользящие окна + заголовки `x-ratelimit-*` + `retry-after`, запас 10%), режет перевод на куски, которые гарантированно влезают в один запрос, и при исчерпании квоты мгновенно переходит на следующую модель — ошибок 429/413 пользователь не увидит. Подробно: **[docs/GROQ_LIMITS.md](docs/GROQ_LIMITS.md)**.

Без `GROQ_API_KEY` бот работает ровно как раньше (только DeepSeek). Описание ниже про DeepSeek относится к резервному пути.

**Резервный путь (DeepSeek).** Если бесплатные модели Groq недоступны или исчерпали квоту, тест пишется **одним дешёвым вызовом**: **deepseek-flash** (DeepSeek-V4.1-Flash) **в thinking-режиме** (`{"thinking":{"type":"enabled"}}` + официальный `reasoning_effort`) пишет весь тест из 20 вопросов, сам проверяя ключи ответов. Усилие адаптивное: chain-тесты (по одному на предмет, общие для всех учеников) — `reasoning_effort=high` («средний» уровень думания), персональные тесты по слабым темам и все ретраи — `low`. Итог ≈ **$0.002–0.006 за тест** (жёсткий потолок одного вызова ~$0.0096 по пиковому тарифу — `max_tokens=8000`, покрывает и скрытые thinking-токены). Старые имена моделей `deepseek-chat`/`deepseek-reasoner` **удалены из API 24.07.2026** и не используются; если thinking-параметры отвергаются (старый прокси) — клиент прозрачно откатывается на **deepseek-v4-pro** (non-thinking, дороже — только fallback). Каждый вызов логирует реальные токены и оценку стоимости (off-peak/peak + сумма за сессию) — чек всегда виден в логах сервера. При пустой цепочке предмета Тест 1 ставится в очередь немедленно при старте. Генерация включена, если задан хотя бы один ключ (`GROQ_API_KEY` или `DEEPSEEK_API_KEY`); без обоих она выключена и предмет останется без тестов.

## Возможности

- **Регистрация**: `/start` создаёт пользователя или обновляет его данные. Deep link `/start <payload>` и форма `/start@BotName` обрабатываются так же, как `/start` (payload пока не используется); то же для остальных команд (`/subjects@BotName` и т.д.).
- **Главное меню** — обычные Reply-кнопки внизу чата: 📚 Предметы · 🎯 Слабые темы · 📊 Статистика · ⚙️ Настройки. Inline-кнопки используются внутри экранов предметов/тестов/результатов.
- **Список предметов** — InlineKeyboard по **1 кнопке в ряд** (на всю ширину, длинные названия читаемы); у каждого предмета **свой эмодзи** (📐 Математика, 📖 Грамотность чтения, 🧬 Биология и т.д.).
- **Предметы задаются в базе данных** — встроенного seed нет: свежая база стартует **без предметов**, их добавляют SQL-запросом (см. «База данных» ниже). Тестов-заглушек нет: всю цепочку каждого предмета строит ИИ (Тест 1, 2, … до 200), начиная с базового уровня школьной программы.
- **ИИ-генерация тестов** — основной провайдер Groq (`openai/gpt-oss-120b`: reasoning medium для chain-тестов, low для персональных и ретраев; вторая и последняя попытка Groq — `qwen/qwen3.8-27b` без рассуждений; тест собирается пакетами по 5 вопросов, см. «Масштабирование генерации»), резерв — один вызов DeepSeek **deepseek-flash** (thinking, high для chain-тестов, low для персональных и ретраев) на тест с адаптивным `reasoning_effort` и жёстким `max_tokens` (предел действует и на скрытые thinking-токены). Экономия достигается так:
  - промты компактные: прошлый тест передаётся строками «тема — короткая суть вопроса (≤80 символов) — уровни ученика», БЕЗ вариантов ответов; поле `why` из JSON-контракта убрано;
  - никакого отдельного шага шлифовки: модель один раз пишет тест и сама проверяет ключи;
  - персональный тест по слабым темам получает только короткие названия тем (пара слов каждая) — промт крошечный;
  - **общий банк вопросов**: два ученика с одинаковыми слабыми темами получают тесты из одних и тех же проверенных вопросов банка — без вызова ИИ (см. «Банк вопросов»);
  - локальный валидатор JSON-контракта (ровно 20 вопросов, 4 варианта, `correct_index` 0–3, без дублей, без перекоса ключей; для weak-теста — строго запрошенные темы, все покрыты) — сломанный ответ никогда не попадает в БД.
- **Цепочка тестов с ПЛАВНОЙ прогрессией сложности**: модель видит прошлый тест с **усреднённым по всем ученикам** уровнем знаний по каждому вопросу (0=не знают, 1=в процессе, 2=закреплено; цепочка общая для всех, поэтому учитываются все, а не один ученик) и получает целевую среднюю сложность для своей позиции с явной шкалой 1–5 и распределением 20 вопросов по уровням. Кривая длинная и плавная: Тест 1 ≈ 1.3 (очень лёгкий), Тест 10 ≈ 2.6, Тест 30 ≈ 3.5, Тест 50 ≈ 3.9, Тест 100 ≈ 4.4, 150+ ≈ 4.7–4.8; шаг между соседними тестами ≤ 0.18. Ответ модели, средняя сложность которого отличается от цели больше чем на 0.75 (было 1.0), где больше 20% вопросов на ≥ 2 уровня от цели или который легче прошлого теста, отклоняется (тест пишет следующий провайдер, получив причину отказа). **Ограничение:** сравнивается сложность, которую модель *сама* проставила вопросам (`difficulty` 1–5) — это защита от явного игнорирования инструкции, а не независимая оценка сложности; реальная сложность косвенно видна только по статистике ответов учеников. Если прошлый тест недоступен, тест №N всё равно генерируется на уровне своей позиции (раньше он молча откатывался к «первому, базовому» тесту).
- **Правило разблокировки**: следующий тест открывается, когда предыдущий доведён до **15🟢 + 5🟡** (закреплено + в процессе) — то есть минимум 15🟢 и остальные минимум 🟡; результат лучше планки (16🟢+4🟡, 20🟢) тоже открывает тест (`models.MeetsUnlockBar`; раньше требовалось строго ≥5🟡, и ученик с 20🟢 оставался заблокирован). Генерация следующего теста запускается ровно в момент достижения планки, один раз на предмет — следующие ученики получают уже готовый тест. Закрытые тесты помечены 🔒, тап по замку показывает, чего не хватает. Проверка устойчива к «дырам» в нумерации цепочки: блокирующим считается первый непройденный тест, поэтому Тест 1 всегда доступен, даже если часть старых тестов удалена.
- **Генерация только тогда, когда это нужно**: тест цепочки генерируется, когда пользователь до него дошёл — при открытии предмета (тест, который уже можно открыть, но его ещё нет) и сразу после разблокировки следующего теста. Такие задачи срочные (urgent игнорируют `not_before` и идут в воркере первыми). Заранее закрытые тесты сейчас **не** предгенерируются; off-peak окно (`GEN_OFFPEAK_START_HOUR`/`GEN_OFFPEAK_END_HOUR`, иначе расписание DeepSeek UTC) применяется только к несрочным задачам, которые код сейчас не ставит. Тап по ⏳ отвечает «Минуточку, тест генерируется…».
- **🎯 Слабые темы (в главном меню)**: персональный тест из 20 вопросов по пяти самым слабым темам. Слабая тема определяется по **накопленной статистике ученика по теме предмета** (`user_topic_stats`: все ответы во всех тестах — цепочка и персональные, все попытки), а не по статусу отдельных вопросов. Оценивается окно из последних 10 ответов темы: меньше 3 ответов — данных мало; 🔴 — ≥2 ошибок и верно < 50%; 🟡 — ≥2 ошибок и верно 50–79%; иначе тема в порядке (одна случайная ошибка никогда не делает тему слабой). Верный повторный ответ на уже 🟢-вопрос не считается (это память о вопросе, а не знание темы). Статистика не удаляется при «🏁 Закончить тест», предметы не смешиваются. Экран показывает темы с 🔴/🟡 и «верно X из Y». После «Закончить тест» следующий тест собирается из банка заново: уже виденные вопросы (есть строка в `user_question_progress`) не выдаются, кроме тех, где у ученика 🔴. Подробно: [docs/WEAK_TOPICS.md](docs/WEAK_TOPICS.md). Тест **свой у каждого ученика** (`kind='personal'`, `owner_user_id`) и создаётся ТОЛЬКО по явному тапу (автогенерации при открытии предмета больше нет). Незаконченная попытка продолжается с того же вопроса; когда тест доведён до 15🟢 + 5🟡, появляется кнопка «🏁 Закончить тест» — тест убирается у ученика, и при следующем заходе собирается новый по актуальным пробелам. Вопросы банка при этом не удаляются (удаляется только строка теста и связи).
- **Экран предмета** — сетка тестов **по 3 в ряд** (а не в столбик), до **200 тестов**, с пагинацией ⬅️ Назад / Вперёд ➡️ (по 12 на страницу). **Страница запоминается**: вышел на 5-й странице — вернёшься на 5-ю. Метки: ✅ пройден на 15🟢+5🟡, ⏸ есть незавершённая попытка, ⏳ тест генерируется, 🔒 закрыт.
- **Очередь генерации** в PostgreSQL (`generation_jobs`): идемпотентная (частичные уникальные индексы не дают задвоить задачи), с ретраями (до 3 попыток, backoff 10 мин) и статусами pending/running/done/failed. Зависшие «running»-джобы (погибший воркер, деплой, OOM) автоматически возвращаются в очередь через 20 минут (живую джобу heartbeat обновляет каждые 2 минуты). Очередь разбирает **пул из `GEN_WORKERS` воркеров** (по умолчанию 4): новая задача будит свободный воркер сразу, воркер после завершения джобы тут же берёт следующую (20-секундный опрос остался только как fallback для задач других инстансов и истёкших backoff). Захват — `FOR UPDATE SKIP LOCKED` с переводом в `running` в той же транзакции, поэтому одна джоба никогда не выполняется двумя воркерами (и при нескольких инстансах). Платный DeepSeek-фолбэк ограничен `GEN_DEEPSEEK_CONCURRENCY` одновременными вызовами. Quality sweep работает в отдельной низкоприоритетной горутине и пропускается/прерывается, пока в очереди есть срочные пользовательские задачи.
- **Новая попытка**: порядок 20 вопросов и порядок вариантов A/B/C/D каждого вопроса перемешиваются и **сохраняются в `attempt_questions`**. Проверка ответа идёт по сохранённому порядку, а не по исходной букве. При продолжении попытки ничего не перемешивается заново.
- **Ответ — одно сообщение на весь тест**: нажатие A/B/C/D сразу показывает всплывашку «🟢 Правильно» / «🔴 Неправильно» (answerCallbackQuery — бесплатно, вне `TG_MAX_RPS`), а **то же самое сообщение редактируется** (ОДИН вызов `editMessageText` на ответ): сверху короткий итог прошлого вопроса («🟢 Правильно» или «🔴 Неправильно — правильный ответ: D) …»), ниже следующий вопрос с клавиатурой. История отвеченных вопросов в чате не сохраняется — это осознанная плата за вдвое больший потолок пропускной способности (≈25 ответов/с вместо ≈12 при `TG_MAX_RPS=28`). Последний ответ превращает это же сообщение в экран результата, затем приходит заметка, возвращающая нижнее меню. Если сообщение отредактировать нельзя (удалено, слишком старое и т. п.), вопрос приходит новым сообщением — тест не застревает; ошибка «message is not modified» игнорируется. Повторные/устаревшие нажатия отсекаются («Ответ уже засчитан» / «Этот вопрос уже неактуален»). Кнопки ответов — полноширинные, с текстом варианта («A) Ответ A»).
- **Система знаний** по паре `user_id + question_id`: 🔴(0) → 🟡(1) → 🟢(2):
  - правильно: 🔴→🟡, 🟡→🟢, 🟢→🟢
  - неправильно: 🔴→🔴, 🟡→🔴, 🟢→🟡
  - плюс счётчики правильных/неправильных ответов.
- **Результат** после 20-го вопроса: 🟢 Закреплено / 🟡 В процессе / 🔴 Требует повторения (состояние вопросов пользователя после прохождения) и «Результат: X/20». Кнопки: 🔄 Пройти тест ещё раз (новая попытка!), 📚 К предметам, ⬅️ Главное меню.
- **Прогресс**: сначала выбор предмета (InlineKeyboard по 1 в ряд, с эмодзи предмета), затем статистика только выбранного предмета — количество 🟢/🟡/🔴 и всего вопросов (нулевая статистика, если предмет не проходили).
- **DeepSeek API**: клиент `internal/deepseek` (OpenAI-compatible chat completions, JSON Output mode). Основная модель — env `DEEPSEEK_REASONER_MODEL` (по умолчанию `deepseek-flash`) в thinking-режиме с `reasoning_effort` high/low по типу задачи; `DEEPSEEK_MODEL` (по умолчанию `deepseek-v4-pro`, non-thinking) — только запасной вариант, если thinking-параметры отклонены прокси. Промты нацелены на подготовку к ЕНТ/УБТ (9–11 классы, школьная программа Казахстана). Без ключа генерация просто выключена.
- **🚪 Выйти**: сначала подтверждение «Выйти из теста?» (✅ Да, выйти / ↩️ Нет, продолжить), чтобы случайный тап не прерывал прохождение. При выходе попытка сохраняется; при повторном открытии теста она продолжается с текущего вопроса.

## 🇰🇿 Фоновый перевод (R-4)

Перевод теста на казахский **никогда не выполняется внутри обработчика апдейта Telegram**:

- Обработчик проверяет кэш (`question_translations`). Полный перевод есть — тест открывается сразу (0 вызовов ИИ). Нет — ставится задача в очередь `translation_jobs` (миграция `000016`) и пользователь получает «⏳ Перевод готовится…»; слот вебхука освобождается за миллисекунды.
- `UNIQUE (test_id, lang)` — одна задача на тест и язык: тест не переводится дважды ни при 32 одновременных открытиях, ни при двух инстансах (zero-downtime деплой). Это заменило старый мьютекс в памяти.
- Задачи разбирают 2 фоновых воркера: захват `FOR UPDATE SKIP LOCKED`, heartbeat каждые 30 с, зависшие задачи (нет heartbeat 3 мин) возвращаются в очередь, до 3 попыток с backoff 2 мин, при SIGTERM задача возвращается в очередь без списания попытки.
- Ожидающих пользователей уведомляет **общий** наблюдатель на тест (не по одному на пользователя): воркер этого инстанса публикует результат мгновенно; задачи, завершённые другим инстансом, ловит один лёгкий запрос статуса задачи раз в 10 с на тест. Ожидание ограничено 4 минутами — потом тест открывается на русском.
- **Chain-тест ставится в очередь перевода сразу после генерации** (тесты цепочки общие, казахоязычные ученики всё равно их откроют). Языковые предметы не переводятся никогда.
- Ошибка перевода не ломает тест: показывается русский оригинал, ошибка пишется в лог. Ключ правильного ответа в модель не отправляется — он берётся из мастер-строки вопроса.

## 🌐 Языковые предметы не переводятся

Настройка «🇰🇿 Қазақша» переводит только обычные предметы (математика, биология, история…). **Языковые предметы** — «Русский язык», «Английский язык», «Казахский язык», литература, иностранные языки — показываются **всегда на языке самого предмета**: их вопросы и варианты ответов — это слова и формы изучаемого языка, и перевод ломает задание (у русской орфографии «в переводе на казахский» нет правильного ответа). Определение по названию предмета — `models.SubjectContentLang`. Генератор для таких предметов пишет тест сразу на нужном языке (английский — на английском, казахский язык — на казахском). Миграция `000010` удаляет ранее закэшированные ошибочные переводы.

Также: обязательный в production `WEBHOOK_SECRET` (проверка заголовка `X-Telegram-Bot-Api-Secret-Token`; без него бот не стартует, если не задан `APP_ENV=development`), таймаут обработки апдейта, мгновенный ответ на нажатие A/B/C/D (кнопка больше не «крутится»), корректная обрезка кириллицы в промпте.

## ✅ Пост-валидация качества вопросов (все предметы)

Генератор больше не выдаёт вопросы, где ответ виден по оформлению вариантов (пример бага: «В каком предложении нужно поставить тире?» — тире было только в правильном варианте).

- **Промт** (`genSystemPrompt`) явно требует: ответ определяется только знанием; варианты одной структуры и формата; в вопросах «где нужен знак/буква» знак не проставлен ни в одном варианте (одинаковый пропуск «_»), в вопросах «где знак поставлен верно» — проставлен во всех; есть пример плохого и хорошего вопроса.
- **Аудит** (`internal/services/quality.go`, `auditQuestion`) — локальная проверка каждого вопроса любого предмета (RU/KK/EN). **Жёсткие** дефекты: правильный вариант — единственный со знаком (тире, запятая, двоеточие, точка с запятой, дефис, кавычки, апостроф, !/?) или единственный без него; нужный знак уже напечатан в части вариантов вопроса «где нужен знак»; единственный заполненный вариант среди вариантов с пропусками («р..сти») и наоборот; единственный с точкой в конце; совпадающие варианты (с учётом регистра, ё/е, точки); варианты, различающиеся только пунктуацией (вне темы пунктуации); «все ответы верны»/«нет правильного ответа»/«all of the above»; пометки «(верно)», «✓». **Мягкие**: ключ сильно длиннее/короче всех дистракторов, ключ дословно повторяет вопрос.
- **Перегенерация**: если в ответе модели больше 6 «жёстких» вопросов — весь ответ отклоняется и тест пишет следующий провайдер. Иначе флагнутые вопросы (до 6 за вызов, 2 раунда) отправляются модели на переписывание с конкретными причинами (`repair.go`); переписанный вопрос снова проходит аудит, тема и сложность закрепляются за исходными. Тест с оставшимся «жёстким» вопросом в БД не попадает (джоба уйдёт в ретрай).
- **Старые тесты**: фоновый sweep раз в 5 минут проверяет ещё не проверенные вопросы в БД (миграция `000011`: `questions.quality_checked_at`, `quality_attempts`), флагнутые переписывает **на месте** (тот же id — прогресс 🔴🟡🟢 и история попыток сохраняются, кэш перевода сбрасывается). Вопрос, открытый в незавершённой попытке, не трогается до её окончания.

## 🔥 Огонёк в статистике

- «📊 Статистика» начинается со строки «🔥 У вас N-й день огонька! (N дней подряд)», дальше — «📊 Ваша статистика по предметам:» со сводкой 🟢/🟡/🔴 по начатым предметам; экран отдельного предмета тоже показывает огонёк. Используется существующий счётчик `users.streak_days` (вторая система не создавалась).
- Исправлено: день огонька считается по календарю Казахстана (UTC+5), а не по UTC базы (раньше «день» менялся в 05:00 и занятие после полуночи засчитывалось во вчера); погасший огонёк (пропущен день) больше не показывается в топе и в таблицах предметов; запоздалый запрос со старой датой не сбрасывает серию и не сдвигает дату назад; старые строки со `streak_days = 0` начинают серию с 1.

### Тесты

`go test ./...` — юнит-тесты (аудит по предметам, правила огонька). С БД дополнительно запускаются интеграционные сценарии (streak по дням, лидерборды, генерация с ремонтом через фейковый Groq, sweep, экран статистики через обработчик):

```
TEST_DATABASE_URL=postgres://user:pass@localhost:5432/test_db?sslmode=disable go test -p 1 ./...
```

`-p 1` — интеграционные пакеты используют одну базу; так они не мешают друг другу. Проверено на PostgreSQL 17 (чистая база и база с уже применёнными 000001–000012).

## UX-исправления (ожидание, слабые темы, главное меню)

- **Ожидание теста — сообщением в чат, а не мини-тостом.** Когда тест переводится на казахский, бот сразу пишет в чат «⏳ Перевод готовится…» и освобождает обработчик (перевод идёт в фоне, см. «Фоновый перевод» ниже); как только перевод готов, заметка удаляется и первый вопрос появляется сам — уже на казахском (если перевод не удался — на русском, с честным сообщением). Когда тест (обычный ⏳ или персональный по слабым темам) ещё генерируется, бот отправляет «⏳ Тест генерируется… никуда не уходи», а фоновый наблюдатель сам превращает это сообщение в «✅ Готово!» с кнопкой «▶️ Начать тест» (или в понятную ошибку с кнопкой «🔄 Попробовать ещё раз»). Повторные тапы не спамят чат. Прочие важные уведомления (например, условие разблокировки 🔒) показываются модальным окном с кнопкой OK.
- **🎯 Слабые темы — только предметы, где слабые темы реально есть.** Предметы без записанных 🔴/🟡 тем в список не попадают, поэтому бесконечной генерации больше нет. Если слабых тем нет нигде — бот так и говорит и предлагает перейти в «📚 Предметы».
- **Главное меню возвращается после теста.** Раньше служебное сообщение с клавиатурой сразу удалялось, и вместе с ним у Telegram-клиента пропадало нижнее меню. Теперь после завершения теста или выхода из него бот оставляет короткую заметку «🏠 Главное меню снова доступно», и нижние кнопки появляются надёжно. Кроме того, в списке предметов и на экране предмета есть кнопка «🏠 Главное меню», так что застрять в предметах нельзя.

## Гарантии

- Ответ не засчитывается дважды при повторном callback (блокировка строки + guard `answered = FALSE` в одной транзакции).
- Проверяется, что попытка принадлежит пользователю.
- Каждый запуск теста — отдельный `test_attempt` (кнопка «🔄 Пройти тест ещё раз» создаёт новую попытку с новыми порядками вопросов и вариантов).
- Все изменения ответа выполняются атомарно в одной PostgreSQL-транзакции; переход статуса 🔴🟡🟢 считается от заблокированного (`FOR UPDATE`) предыдущего статуса.
- Секреты — только через переменные окружения.
- Миграции применяются автоматически при старте (embedded SQL).
- Генерация не может задвоиться: частичные уникальные индексы на `generation_jobs` + `ON CONFLICT DO NOTHING`; параллельная постановка `topic_batch` одной темы отсекается уникальным частичным индексом по `(subject_id, topic_key)`; второй персональный тест того же ученика — индексом `idx_tests_personal_owner` (проигравший гонку читает готовый тест).
- Сломанный ответ модели никогда не попадает в БД: строгая валидация JSON-контракта до записи; сбой reasoner откатывается на валидный черновик.
- Задачи генерации не блокируют UI: все вызовы DeepSeek идут только в фоновом воркере.

## База данных

Таблицы: `users`, `subjects`, `questions`, `tests` (+`kind`, `topics`, `owner_user_id`, `from_bank`), `test_questions`, `test_attempts`, `attempt_questions`, `user_question_progress`, `user_subject_state` (страница сетки тестов, водяные знаки цепочки), `generation_jobs` (очередь ИИ-генерации: `chain`, `personal`, `topic_batch`), `user_topic_stats`, `subject_topics`, `topic_aliases`, `question_translations`, `translation_jobs`, `ai_spend_daily`, `app_backfills`, `schema_migrations`.

Миграции: `migrations/000001` … `000024` (последняя — `000024_generation_scale`: `test_templates`, `test_template_uses`, `gen_job_batches`, `gen_strategy_stats`, `generation_jobs.strategy`, индексы `idx_user_topic_stats_subject_updated`, `idx_genjobs_active_kind`). Номера уникальны и идут подряд — это проверяет `TestMigrationVersionsUniqueAndContiguous`, а `database.Migrate` отказывается стартовать при двух файлах с одним номером. Новая миграция получает следующий свободный номер (сейчас — `000027`; `000025` — очередь апдейтов кластера, `000026` — подписки Stars). Применённые версии записываются в `schema_migrations` и повторно не выполняются; параллельный старт двух инстансов сериализуется `pg_advisory_lock`.

**Seed предметов нет, папки с готовыми вопросами тоже нет.** На свежей базе таблица `subjects` пуста (миграция `000002` удаляет старые сид-предметы, `000004` — старые тесты-заглушки), бот при старте пишет в лог предупреждение, а «📚 Предметы» показывает «предметов пока нет». Все вопросы пишет ИИ.

**Как добавить предмет:** вставить строку в `subjects` (`name` уникален, `position` задаёт порядок в списке), затем перезапустить бота или просто открыть предмет в боте:

```sql
INSERT INTO subjects (name, position) VALUES ('Математика', 1) ON CONFLICT (name) DO NOTHING;
```

Эмодзи предмета подбирается по названию (`subjectEmoji`); языковые предметы («Русский язык», «Английский язык», «Казахский язык», литература) не переводятся (`models.SubjectContentLang`).

При следующем старте для каждого предмета с пустой цепочкой Тест 1 сразу ставится в очередь генерации (если включён ИИ-провайдер); кроме того, тест генерируется срочно при первом открытии предмета пользователем. Дальше цепочку продолжает генератор.

**Банк вопросов (B3–B6).** Все проверенные вопросы предмета (`quality_checked_at IS NOT NULL`, с `topic_key`) образуют общий банк. Персональный тест «🎯 Слабые темы» — это одна строка `tests` (`kind='personal'`, `owner_user_id`, `from_bank = TRUE`) со ссылками `test_questions` на вопросы банка: квоты делятся поровну между слабыми темами (5 тем × 4 = 20), берутся только вопросы, которых ученик не видел (нет строки в `user_question_progress`) или где у него 🔴. Ни вызова ИИ, ни новых строк `questions` под ученика. Прогресс личный — `user_question_progress (user_id, question_id)`, поэтому общие вопросы не смешивают учеников.
- **Нехватка банка.** Если какой-то теме не хватает вопросов, ставится задача `topic_batch` (≈10 вопросов, `TopicBatchSize`) ТОЛЬКО на недостающие темы; дубли отсекает уникальный индекс по активным задачам. Ученик видит ожидание; после завершения пакета наблюдатели повторяют сборку. Провал/таймаут — сообщение с кнопкой «Обновить». Если тема не покрывается пакетами (нет в справочнике, кулдаун), запасной путь — обычная персональная генерация (с дневным лимитом на ученика).
- **Пополнение банка.** Вопросы `topic_batch` проходят тот же аудит качества и сохраняются с `topic_key` и `quality_checked_at = now()` (дубли текста внутри темы пропускаются). Вопросы chain-тестов после успешного аудита получают `topic_key` через `ResolveTopicKey` (не сопоставилось — NULL) и тоже видны банку; старые chain-вопросы привязываются одноразовым бэкфиллом через алиасы.
- **Справочник и алиасы.** Тема вопроса сопоставляется с банком только через `topic_key`: сырое название → `models.NormalizeTopic` → `topic_aliases` → `subject_topics`. Чтобы банк «увидел» новое написание темы, достаточно добавить алиас (SQL ниже).
- **`TG_MAX_RPS`** (по умолчанию 28) — общий token bucket на исходящие send/edit/delete-запросы к Telegram; вызовы ждут слота, при 429 приостанавливается весь ограничитель.

**Справочник тем (B1):** `subject_topics` (канонические темы предмета, `topic_key` = нормализованное название) и `topic_aliases` (все известные написания → `topic_key`); у вопросов колонка `questions.topic_key`. При первом старте справочник один раз заполняется из существующих вопросов (темы, которые встречаются хотя бы у 3 вопросов). ИИ получает список тем предмета и обязан брать тему из него (у chain-теста допускается не больше 2 новых тем — они добавляются в справочник). Добавить тему и алиас вручную:

```sql
INSERT INTO subject_topics (subject_id, topic_key, title) VALUES (1, 'генетика', 'Генетика') ON CONFLICT DO NOTHING;
INSERT INTO topic_aliases (subject_id, alias_norm, topic_key) VALUES (1, 'генетика', 'генетика'), (1, 'наследственность', 'генетика') ON CONFLICT DO NOTHING;
-- привязать старые вопросы с новым алиасом:
UPDATE questions SET topic_key = 'генетика' WHERE subject_id = 1 AND topic_key IS NULL AND lower(topic) = 'наследственность';
```
`alias_norm` — название в нижнем регистре с одиночными пробелами (`models.NormalizeTopic`).

## Масштабирование генерации (тысячи учеников)

- **Одинаковые тесты для одинаковых слабых тем.** Отпечаток (`models.WeakTopicsFingerprint`) — SHA-256 от предмета и отсортированного набора `topic_key` слабых тем. (1) Банк вопросов выбирает кандидатов в псевдослучайном порядке, заданном отпечатком (`md5(fingerprint:id)` вместо `random()`), — два ученика с одинаковыми слабыми темами и одинаковой историей получают один и тот же набор общих вопросов банка. (2) Если банк не может собрать тест, тест генерируется ИИ ОДИН раз и сохраняется как шаблон (`test_templates`, JSON-контент); следующий ученик с тем же отпечатком сразу получает **клон**: новая строка `tests` + НОВЫЕ строки `questions` с тем же содержимым (прогресс строго личный, кэш казахского перевода копируется) — без ИИ, без очереди и без списания дневного лимита. Один шаблон одному ученику дважды не выдаётся (`test_template_uses`); повторный запрос с теми же темами создаёт новый вариант. (3) Для цепочки отпечаток = предмет + номер + предыдущий тест + слабые темы: повторная генерация того же слота с теми же входными данными клонирует шаблон (`GEN_TEMPLATE_REUSE=false` отключает). Неиспользуемые 90 дней шаблоны удаляет ежесуточная очистка.
- **Прошлый тест и слабые темы в цепочке.** Генератор цепочки берёт прошлый тест (`findChainTest(N-1)`), средние метки учеников по вопросам (0/1/2) и по темам, объединяет слабые темы прошлого теста (средняя метка < 1.0) с общими слабыми темами предмета (агрегат `user_topic_stats` активных за 30 дней учеников, ≥ 3 ученика на тему, кэш 10 мин) и требует покрыть минимум 3 из них. Жёсткая валидация на КАЖДОМ шаге, а не только в конце: повтор вопроса прошлого теста (точный или перефразированный, Jaccard ≥ 0.8) и почти-дубли внутри теста, покрытие слабых тем, средняя сложность ±0.75 (было ±1.0), не более 20% вопросов на ≥ 2 уровня от цели, тест не легче прошлого (floor = min(прошлая средняя, цель) − 0.3).
- **Пакетная генерация.** Тест планируется как 20 «слотов» (тема + уровень сложности из кривой), пакет из 5 вопросов получает точную спецификацию каждого вопроса. Каждый вопрос проверяется отдельно: годные сохраняются (`gen_job_batches`), заново запрашиваются только недостающие слоты; повтор задачи после сбоя/деплоя переиспользует уже оплаченные вопросы. Отклонённый ответ передаётся следующему шагу с причиной («сложность не по спецификации: 3») — ИИ чаще всего игнорирует инструкции именно на «слепом» повторе. Маршрут — не более 2 попыток Groq, затем DeepSeek (`genBatchMaxTokens` 3500, `groqBatchMinTokens` 2000, таймаут шага Groq 90 с). Полная стратегия: `genMaxTokens` 6000 (было 8000), `groqGenMinTokens` 3000 (было 4500), маршрут цепочки GPT-OSS(medium) → Qwen → DeepSeek. Длинный префикс промта одинаков во всех пакетах задачи (кэш промтов Groq/DeepSeek), в логе Groq видно `cached N`.
- **A/B и метрики.** `generation_jobs.strategy` + суточная таблица `gen_strategy_stats` (успехи/провалы, вызовы ИИ, отклонения, нарушения сложности, повторы, попадания в шаблон, токены, время) по стратегии и виду; строка лога `genstats …` на каждую задачу; нарушения сложности — строка `difficulty_violation task=… step=…` и счётчик `gen_difficulty_violations_total` в `/metrics`. Сравнение веток: `SELECT strategy, kind, sum(jobs_done), sum(jobs_failed), sum(ai_calls), sum(difficulty_violations) FROM gen_strategy_stats GROUP BY 1,2;`.
- **Нагрузка.** Вставка вопросов теста — один pipeline (`pgx.Batch`) вместо 40 последовательных запросов; индексы под агрегат слабых тем и подсчёт активных задач; backpressure очереди персональных генераций (`GEN_MAX_ACTIVE_PERSONAL`); идемпотентность вебхука по `update_id` (окно 10 000 последних, повтор подтверждается 200 без обработки, отказ 503 не запоминается); keepalive-пинг LISTEN-соединения раз в 60 с (полуоткрытое TCP больше не «вешает» слушателя); резерв пула растёт с `GEN_WORKERS`.

## Кластер: web + N worker (ROLE)

По умолчанию `ROLE=all` — всё в одном процессе, поведение прежнее, Redis не нужен. Для горизонтального масштабирования процесс делится на роли (подробно — [docs/CLUSTER.md](docs/CLUSTER.md)):

- `ROLE=web` — только приём вебхука: проверка секрета → запись апдейта в общую очередь → мгновенный 200; `/health`, `/ping`, `/metrics`.
- `ROLE=worker` — без вебхука: обработка апдейтов из очереди + генерация, перевод, reaper'ы, quality sweep, очистка.
- Очередь апдейтов (`QUEUE_BACKEND=postgres`, таблица `tg_update_queue`): идемпотентность по `update_id` в БД, порядок апдейтов одного пользователя сохраняется (два апдейта одного пользователя никогда не обрабатываются параллельно), `FOR UPDATE SKIP LOCKED` + `NOTIFY`, lease/heartbeat/reaper для апдейтов умерших воркеров, ретраи с backoff и dead-letter, backpressure (`UPDATE_QUEUE_MAX` → 503).
- Лимит Telegram между инстансами: `RATELIMIT_BACKEND=postgres` делит `TG_MAX_RPS` между живыми воркерами (`cluster_instances`), `redis` — один общий token bucket.
- Redis опционален: пустой `REDIS_URL` → не используется; включается только явным `QUEUE_BACKEND=redis` / `RATELIMIT_BACKEND=redis` / `CACHE_BACKEND=redis`.

## ⭐ Подписки Telegram Stars

Подробно — [docs/SUBSCRIPTIONS.md](docs/SUBSCRIPTIONS.md). Кратко:

- Тарифы:
  - Free — 1 прохождение в день;
  - Plus — 10⭐ в месяц, 4 в день;
  - Pro — 40⭐ в месяц, 10 в день;
  - Premium — 50⭐ в месяц, 20 в день.

  Цены и лимиты задаются в env (`PLAN_*`). Новый день начинается в полночь по `QUOTA_TZ` (Asia/Almaty).
- Прохождение списывается только в момент итогового результата: все вопросы отвечены. Списание атомарно и идемпотентно (`test_completions`, PK `attempt_id`). Брошенный тест ничего не списывает. Повторное прохождение — новое прохождение.
- Когда лимит исчерпан, новый тест не начать: бот показывает, когда лимит сбросится, и кнопку «⭐ Улучшить план». Начатый ранее тест можно доделать.
- Подписка оформляется через `createInvoiceLink` (`XTR`, `subscription_period=2592000`). Платёж применяется один раз по `telegram_payment_charge_id`. Продления приходят как `is_recurring`. Отмена или истечение — пользователь сам возвращается на Free, когда пройдёт `expires_at`. Апгрейд применяется сразу, даунгрейд — только после окончания текущего плана.
- Тест по слабым темам стоит 10⭐ (`WEAK_TEST_PRICE_STARS`), дневной лимит не тратит. Генерация запускается только после `successful_payment`. Если она не удалась — повторная попытка без доплаты, затем автоматический `refundStarPayment`.
- Админ-команды `/grant`, `/revoke`, `/subinfo`, `/refund` работают для Telegram id из `ADMIN_IDS`.
- `SUBSCRIPTIONS_ENABLED=0` возвращает прежнее поведение без лимитов.

## HTTP

- `GET /health` — проверка живости (включая ping БД и, если используется, Redis)
- `GET /metrics` — счётчики генерации в формате Prometheus (нарушения сложности, отклонённые ответы по классам, исходы задач по стратегиям, попадания в шаблоны, backpressure, дубли апдейтов). С `METRICS_TOKEN` требует `Authorization: Bearer <token>` (или `?token=`). Раз в 15 минут сводка пишется в лог строкой `metrics: …`.
- `GET /ping` — лёгкий keep-alive endpoint (только в коде, в интерфейсе бота не отображается). Встроенный self-ping каждые 5 минут обращается к `WEBHOOK_URL/ping`, чтобы сервис не засыпал на бесплатном тарифе Render и фоновый воркер генерации продолжал работать.
- `POST /telegram/webhook` — приём обновлений Telegram (`ROLE=all|web`; у `ROLE=worker` эндпоинта нет)

## Нагрузка, Telegram 429 и лимиты (R-2 / R-3 / R-9)

- **Меньше запросов на ответ (R-2).** Вопрос попытки грузится одним запросом (`LoadQuestionView`: попытка с проверкой владельца + `attempt_questions` JOIN `questions` + перевод вопроса); `TestViewMeta` неизменна в течение попытки и кэшируется в памяти (для казахского — перечитывается, пока перевод не полный). Итог теста — один запрос (`LoadSummary`) вместо пяти. `CreateAttempt` пишет все вопросы одним `INSERT ... SELECT unnest(...)`. Транзакция ответа (`FOR UPDATE`, guard `answered = FALSE`, проверка владельца и порядка) не менялась.
- **Клавиатура (R-2).** Повторное скрытие меню в уже «скрытом» чате — 0 запросов к Telegram; служебное сообщение и старая заметка удаляются одним `deleteMessages`.
- **Webhook (R-3).** Фиксированный пул из 32 воркеров + ограниченная очередь на 1000 апдейтов. Переполнение → мгновенный **HTTP 503** с `Retry-After` (Telegram повторит доставку позже); горутины до семафора больше не создаются. При остановке очередь дочищается.
- **Telegram 429 (R-3).** `retry_after` ≤ 1 с ждётся на месте; длиннее — `sendMessage`/`editMessageText`/`deleteMessage(s)` уходят в фоновую очередь отложенной отправки (по чату, с соблюдением `retry_after`, лимит 1000), слот обработчика не блокируется; `answerCallbackQuery` при длинном 429 не ждёт вовсе.
- **Анти-абьюз (R-9).** Не чаще одного действия пользователя в `USER_ACTION_INTERVAL_MS` (лишний тап только подтверждается, без запросов к БД). ⚠️ По умолчанию этот лимит **в памяти инстанса**: при N инстансах пользователь может получить до N действий за интервал (в кластере апдейты одного пользователя и так обрабатываются строго последовательно); с `RATELIMIT_BACKEND=redis` лимит общий для всех инстансов. Лимиты, которые обязаны быть строгими, хранятся в PostgreSQL: персональные генерации на пользователя в день (`generation_jobs`) и дневной cap DeepSeek.
- **DeepSeek spending cap (R-9).** Перед каждым платным вызовом резервируется худшая стоимость (вход по размеру запроса, весь `max_tokens`, peak-тариф) атомарным `UPDATE ... WHERE cost + reserved + x <= cap`; после ответа резерв заменяется той же оценкой стоимости, что пишется в лог. При достижении cap вызов не отправляется, задача генерации откладывается (попытка не сгорает) до бесплатной квоты Groq или следующего UTC-дня. Ошибка учёта = отказ (fail closed). Бесплатные сценарии (Groq, кэш переводов, сборка из банка) не затрагиваются.

| `SUB_GRACE_MIN`, `WEAK_ORDER_TIMEOUT_MIN`, `WEAK_ORDER_MAX_GEN`, `BILLING_RECONCILE_SEC` | (опционально) запас после истечения плана (60 мин), автовозврат неготового заказа (45 мин / 3 попытки), тик сверки (60 с) |
| `TELEGRAM_TEST_ENV` / `TELEGRAM_API_URL` | (опционально) тестовая среда Telegram (тестовые Stars) / другой Bot API server |

Очереди генерации и перевода работают через LISTEN/NOTIFY: при постановке задачи шлётся `pg_notify` (`gen_jobs` / `tr_jobs`), а отдельная горутина держит ОДНО выделенное соединение с `LISTEN` и сразу будит воркеры; запасной опрос очереди — раз в 3 минуты. `LISTEN` не работает через transaction-mode pooler, поэтому слушатель использует ПРЯМУЮ строку подключения — ту же, что и миграции (`MIGRATION_DATABASE_URL`, иначе `DATABASE_URL` без `-pooler` у хоста Neon); при обрыве соединение переподключается с паузой.


## Деплой на Render (Docker)

1. Создать Neon PostgreSQL и скопировать `DATABASE_URL`.
2. Render → New → Web Service → Docker (репозиторий подключается как есть).
3. Задать переменные окружения: `BOT_TOKEN`, `DATABASE_URL`, `WEBHOOK_SECRET` (любая случайная строка, без него бот в production не стартует), `WEBHOOK_URL` (URL, который выдаст Render, вида `https://<name>.onrender.com`), плюс `GROQ_API_KEY` (бесплатная ИИ-генерация и перевод) и `DEEPSEEK_API_KEY` (платный резерв).
4. После деплоя бот сам применит миграции (включая удаление старых тестов-заглушек), выставит webhook и запустит пул воркеров генерации.
5. Масштабирование (web + N worker): тот же образ — Web Service с `ROLE=web` и Background Worker(ы) с `ROLE=worker`; пошагово — [docs/CLUSTER.md](docs/CLUSTER.md#деплой-на-render-web--n-worker).
5. Добавить предметы SQL-запросом `INSERT INTO subjects ...` (см. «База данных») — встроенного seed нет. Для предметов с пустой цепочкой Тест 1 ставится в очередь генерации при старте и при первом открытии предмета.
